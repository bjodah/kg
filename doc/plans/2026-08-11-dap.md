# DAP support: native debugger client, first adapters lldb-dap and debugpy

Status: reviewed plan, 2026-08-11. This replaces the exploratory draft that
lived in `doc/kg-dap.md` (now a pointer here). The draft's central bet —
native C client sharing LSP's framing and JSON, Lisp as a thin
customization layer on top — survived review and was **validated by a
working prototype**; its initialization choreography, several of its repo
claims, and its sizing of the prerequisites did not. Corrections are
inlined where they matter and the stage detail lives in `doc/plans/dap/`.

An independent implementation-readiness review (2026-08-11, with its own
adapter probes) was incorporated into these documents the same day: it
corrected the thread-stop default, the session-end semantics, the
stale-reference epoch timing and a pre-session keymap contradiction, and
it contributed the config-schema, build-seam, breakpoint-synchronization
and bounds contracts now inlined below and in the subplans.

Provenance discipline: every repo fact below was checked against the tree
on 2026-08-11 and carries file:line. Every claim marked **[MEASURED]** was
observed on this box by driving the real adapters — lldb-dap 21.1.8
(`/opt-2/llvm-21/bin/lldb-dap`) and debugpy 1.8.21 — including a C
prototype (~1000 lines, of which ~285 are the actual client core) that ran
the full choreography (initialize → launch → setBreakpoints →
configurationDone → stopped → threads/stackTrace/scopes/variables →
evaluate → next → continue → disconnect) against both adapters **over
kg's own `src/lsp_transport.c` + `src/lsp_json.c`, byte-for-byte
unmodified**, linking three objects and no editor state. Prior art read in
full: svaante/dape 0.27.1 (the model), emacs-lsp/dap-mode (the
cautionary contrast), and the DAP specification.

## Goal

From a C/C++ or Python file: `F9` sets a visible breakpoint, `dap-debug`
launches the program under the adapter, the program runs to the
breakpoint, kg highlights the stopped line, step/next/finish/continue
work, `dap-evaluate` answers, M-up/M-down walk the stack, and `F12`
toggles a gdb-many-windows-style layout (stack, locals, output,
breakpoints panes) and restores the previous window arrangement on exit.
Everything before that is infrastructure; everything after it
(conditional/log breakpoints, watches, memory, disassembly, child
sessions, Java) is enhancement.

Must-have adapters: `lldb-dap` (C/C++) and `python -m debugpy.adapter`
(Python). Java is a recorded follow-on, not a v1 target — see
"Follow-ons".

Scope discipline, in the LSP plan's mold (`doc/plans/2026-08-08-lsp.md`):
DAP is independent of Lisp, tree-sitter *and LSP* — it must work in
`WITH_LISP=0` and `WITH_LSP=0` builds and carries no `KG_USE_*`
conditionals in editor modules. dap-mode's deepest structural mistake is
storing debug sessions inside lsp-mode's workspace (dap-mode.el:325-331);
kg will not repeat it. The one sanctioned LSP↔DAP seam is the future Java
port-discovery hook (follow-ons), designed as a narrow function pointer so
`dap_core` never learns an LSP method name.

## Verified repo facts this plan builds on

Checked against the tree on 2026-08-11.

- **The transport premise holds.** `src/lsp_transport.h:14-18` says it
  outright: the module "knows nothing about JSON, about requests and
  responses, or about which server is on the other end". The prototype
  drove both real adapters through it unmodified. DAP's `Content-Length`
  framing is byte-identical to LSP's; neither adapter sent `Content-Type`
  or any header the parser doesn't already skip. **[MEASURED]**
- **But reuse needs two new entry points, not a rename.**
  `lsp_transport_start_wire()` always forks a child
  (src/lsp_transport.c:851); the TCP connect (`connect_start()`,
  src/lsp_transport.c:605-628) is `static`, loopback-hardcoded, port-only,
  IPv4-only, and is a phase of the nbcode announce state machine. DAP
  attach needs "connect to host:port, no child, no handshake", and the
  session teardown needs a stdin half-close: after a successful
  `disconnect`, **debugpy's adapter never exits** (measured 30 s linger,
  transport still healthy) while lldb-dap exits immediately —
  end-of-session must not be keyed on EOF. **[MEASURED]**
- **`lsp_json` is generic and sufficient** (src/lsp_json.h:6-33): the
  NULL-tolerant `lsp_json_get()` chaining and `LSP_JSON_NONE` vs
  `LSP_JSON_NULL` (absent ≠ false, which capability parsing needs) are
  exactly right. Gaps: no float writer (`lsp_jsonw_int` only — fine for
  v1) and no tree→writer serializer, which the launch-config passthrough
  wants (validate-parse then `lsp_jsonw_raw()` is the v1 answer).
- **There is no generic async-fd mechanism to extend — LSP is the only
  fd contributor.** The idle seam is src/tty.c:763-770 (`lsp_wait_fds` →
  `kg_idle_wait`) and src/tty.c:805-811 (`KG_IDLE_FD` → `lsp_poll()`,
  "A server, and only a server"); `kg_idle_wait()` itself is already
  generic. `process_table`, `compile` and `autorevert` are tick-only
  (src/tty.c:724-731) and `process_table.h` exposes no fd at all. **Poll
  sites are two, not one**: `lsp_poll()` is also called at
  src/main.c:236-240, and `editor_async_poll()` must land at both or DAP
  events stall behind a keystroke (the LSP plan hit exactly this).
- **The F-key work is a parser rewrite, not added cases.** `enum
  key_base` has only F3/F4 (src/keyevent.h:48-49). Modifier decoding
  hardcodes `;5` = Ctrl and `;2` = Shift with per-final-byte switches
  (src/tty.c:539-635); **no Meta (modifier 3) CSI decoding exists
  anywhere**, and modified two-digit params (`ESC[15;5~`, i.e. every
  modified F5-F12) fall through to `bare_esc()` today. `parse_escape()`
  needs a generic parameter collector + xterm `1+bitmask` modifier
  decode.
- **The user-config story is better than the draft believed.** Lisp
  `define-key` does *not* go through keybind.c's C-c-only gate; it routes
  `keymap_bind()` → `key_parse()` and accepts any sequence the built-in
  maps could hold (doc/lisp-api.md:645-655; `kbd` is the identity,
  lisp/prelude.el:1393). The *only* blocker for
  `(define-key 'dap-mode-map "<f5>" 'dap-step-in)` is that `<f5>` is
  missing from `key_names[]` (src/keyevent.c:79-97). Two traps: the
  define-key fallback creates missing maps at `KEYMAP_LAYER_MAJOR`
  (src/lisp_cmd.c:733), so the `dap` minor map must be created by
  `dap_init()` at startup, never lazily; and `KEYMAP_LAYER_MINOR` has
  **zero production users today** (only test/test_keymap.c) — DAP is its
  first shipped consumer, which is a risk to test, not a solved problem.
- **Keymap capacity has a third bound the draft missed**: beyond
  `keymap_max_maps = 15` and 256 entries, a **2560-byte name pool**
  shared by map names and every interned command name, historically "the
  tightest of the three bounds" (src/keymap.c:13-34) with ~500 bytes
  free. ~14 `dap-*` command names is ~200 bytes of it. Raise it
  alongside the map count, with the rationale in the commit.
- **Windows**: `MAX_WINDOWS 8` (src/def.h:295) and `win_reflow()`'s
  column-group model (src/winmgr.c:103-218) can represent a 2×3 grid with
  per-column window counts — but **all columns get equal width** and
  there is no resize API. No window-configuration save/restore exists;
  `struct editor_window` owns an opaque `vgeom` pointer whose copy-safety
  both split functions warn about (src/winmgr.c:452-457, 502-504). And
  **there is no `src/winmgr.h`** — every `win_*` declaration lives in
  def.h:529-548, which CLAUDE.md forbids growing, so the window-config
  API forces the header migration first.
- **Decorations are the right annotation layer**: marker-anchored with
  per-endpoint gravity, swept by `kg_decor_compact()` after edits
  (src/decor.h:88-125). Adding a face is three edits (enum
  src/decor.h:32-37, range check src/decor.c:34-35, `decor_face_to_hl()`
  src/display.c:205-218) plus an `HL_*` colour. In-tree precedent says
  add a face only when the *colour* is new (src/lsp_diag.c:363-364). The
  only bound is `KG_ROW_DECOR_MAX 16` per rendered row.
- **Build axis precedent is exact**: `WITH_LSP ?= 1` (Makefile:175), one
  shared feature stamp whose *name* gains each axis (Makefile:194), `kg
  -V` feature words (src/main.c:150-162), and `requires_feature:` costs
  nothing once `-V` says `+dap` (utils/pty_accept.py:1027-1028). The
  disabled-build lane to mirror is `.ci/ci-14-with-lsp-0.sh`, which also
  runs orthogonality builds.
- **Ratchets, corrected**: scc sits at exactly 8464/8464
  (Makefile:585-586) — tests offset nothing (scc counts `src/` only), so
  **every stage raises `SCC_COMPLEXITY_MAX` explicitly** with bisect
  proof in the commit message. `PMCCABE_NEW_FUNCTION_MAX = 15`
  (Makefile:600) is a hard design constraint on the protocol dispatcher
  — table-driven, not switch-cascaded. Coverage treats new files as
  notes, not failures; re-bank at feature end. The mutation gateway is a
  non-event *if* `dap_ui.c` writes special buffers through the edit
  gateway — state that as a design constraint. cmdtable rules
  (test/test_cmd.c): sorted unique, summary ≤ 60 columns no trailing
  period, and **two locked audit arrays** — every DAP command needs
  either `CMD_LISP_CALLABLE` or a `not_lisp_callable[]` entry, and
  `dap-evaluate` (it prompts) needs `CMD_READS_TERMINAL` plus a
  `reads_terminal[]` entry.
- **Help/docs**: `utils/check_help_drift.py` requires every help-table
  key to be bound in `src/kbd.c`'s tables — DAP keys live in a minor map
  it can't see. v1 documents keys in `doc/kg.1` and README only, or
  teaches the script the new map in the same commit.
- **Request-correlation machinery to copy, not reinvent**:
  `lsp_client.c`'s flat pending table (slot copied out and cleared
  *before* the callback runs, so callbacks may issue requests;
  src/lsp_client.c:408-455), `CLOCK_MONOTONIC` deadlines restarted on
  handshake (src/lsp_client.c:554-628), the exactly-once callback
  contract (src/lsp_client.h:249-276), and `lsp_req.h`'s
  `sent_generation` guard — the direct in-tree ancestor of this plan's
  `stop_epoch`.
- **No SIGCHLD handler exists, by design** — DAP reaps its own adapter
  with poll-driven `waitpid(WNOHANG)` like every other subsystem
  (src/process.h:100-103).
- **Test hooks that already exist**: PTY `env:` with `{REPO}`,
  `workspace_files:` with `{CWD}`, `config_files:`, `requires_tool:`,
  `requires_feature:` (utils/pty_accept.py:108-112, 472-501). The
  env-injection precedent is per-server (`KG_LSP_SERVER_<MODE>`,
  src/lsp_server.h:135-159) — DAP mirrors it as `KG_DAP_ADAPTER_<MODE>`
  so C++ and Python cases can inject different fakes in one build.
  **The PTY harness has no F-key tokens** — adding `<f5>`-style tokens
  (and modified forms) is a deliverable, not a given.
- `MAX_BUFFERS 20` (src/def.h:330): ~9-11 special buffers are already
  reachable simultaneously; six `*dap-*` buffers genuinely exhaust it.
  1968 bytes/slot measured, so 20 → 32 costs ~24 KB BSS; sibling arrays
  at event.c:38, bufmgr.c:2091, bufmgr.c:2126. Its own commit.
- **Nothing in the tree references DAP today.** The one adjacent string
  is the nbcode announce comment: the same child process announces
  `Java Language Server listening ...` and
  `Debug Server Adapter listening ...` (src/lsp_transport.h:100-104) — a
  comment and test fixture, not code, but a real clue for the Java
  follow-on.

## Measured protocol facts the design is built around

These were observed live against both v1 adapters; each shapes a specific
piece of the design. The fake adapter must have a scripted mode for every
one of them.

1. **The launch/attach response has no fixed position.** lldb-dap answers
   `launch` *before* the `initialized` event; debugpy answers it *after*
   the `configurationDone` response; nbcode and delve answer between the
   two (after `initialized`, before `configurationDone` — measured for
   subplans 03/04). Four adapters, three distinct orderings. A client
   that waits on the launch response before configuring deadlocks
   debugpy; one that requires `initialized` first mis-sequences
   lldb-dap. Therefore: send
   `launch`/`attach` from the `initialize` response handler,
   fire-and-report-error with **no deadline** (dape ships exactly this,
   dape.el:1724), and drive configuration solely off the `initialized`
   event. RUNNING is reachable idempotently from either the launch
   response or the `configurationDone` response.
2. **Do not advertise `supportsRunInTerminalRequest` in v1.** debugpy's
   upstream default console (`integratedTerminal`, dape.el:155) triggers
   the reverse request on *every* launch, and advertising-then-refusing
   **hangs both adapters** — neither ever answers `launch` (measured;
   debugpy hangs silently forever, lldb-dap stalls ~20 s). Not
   advertising yields an immediate, quotable launch failure from both.
   kg's debugpy config defaults `"console": "internalConsole"`, which
   routes debuggee I/O through `output` events — what a terminal-less
   client wants anyway.
3. **Do not advertise `supportsStartDebuggingRequest`; if a reverse
   request arrives anyway, answer `success:false` — never
   accept-and-ignore, never stay silent.** Measured: refusing lets a
   debugpy child run undebugged and the session completes; accepting
   without connecting deadlocks the debuggee (the child config's
   `connect:{host,port}` is a promise). Silence hangs the adapter —
   dap-mode has exactly this bug (no default clause,
   dap-mode.el:1132-1135). Cost of not advertising: Python
   subprocess/multiprocessing debugging, deferred to a follow-on; kg's
   debugpy config also defaults `"subProcess": false`.
4. **The suspension epoch is mandatory, not defensive.** After resume +
   re-stop, both adapters answer *stale* `variablesReference`/`frameId`
   handles with `success:true` and silently wrong or empty data (lldb-dap
   reuses the same small integers every stop; delve, alone of the four,
   errors). No error ever says "stale". Every
   `stackTrace`/`scopes`/`variables`/`evaluate`/`setVariable`
   continuation carries the epoch and late replies are dropped. The epoch
   bumps **before** any resume-implying request is sent, on an accepted
   `stopped`, on an unsolicited `continued`, and on session death — a
   bump only-on-stop would let a late reply land in the window between
   continue and the next stop. A separate *selection generation* guards
   same-stop races: a scopes reply for frame A must not paint locals
   after the user selected frame B, which the epoch alone cannot see.
5. **Two independent seq spaces, and the adapter's may be garbage.**
   lldb-dap stamps `seq: 0` on *every* response and event. Match
   responses by `request_seq` only; key inbound reverse requests
   separately (echo even a zero `request_seq` back); tolerate a string
   `seq` (netcoredbg, per dape.el:1614-1615).
6. **Error extraction is two-headed**: debugpy puts failures in
   `message`, lldb-dap *only* in `body.error.format` (+`showUser`). Read
   `message`, then `body.error.format`, then synthesize.
7. **Capabilities are mutable and misspelled.** lldb-dap adds
   `supportsRestartRequest` and `supportsStepInTargetsRequest` via a
   `capabilities` *event* ~15 ms after an initialize response that
   omitted them — merge, never replace (dape fixed this in 0.22).
   debugpy spells the spec's `supportTerminateDebuggee` as
   `supportsTerminateDebuggee`; parse both. Absent ≠ false
   (`LSP_JSON_NONE` is the right test). Measured v1 matrix: lldb-dap has
   **no `terminate`**, no `gotoTargets` (debugpy has both); neither has
   `restart` at initialize; both have `configurationDone`,
   conditional/hit/log breakpoints, `setVariable`,
   `supportsDelayedStackTraceLoading`, exception filters (debugpy's
   `uncaught` defaults **true** — honoring filter defaults gives Python
   uncaught-exception stops for free).
8. **Teardown is a lattice, and `exited` is not on it.** Per the spec,
   `exited` reports the debuggee's exit code — status, not session end;
   `terminated` ends the session (and may carry a `restart` value to
   retain). The session moves to DEAD on any of {`terminated` event,
   matched `disconnect` response, transport EOF/failure, a forced-close
   grace deadline}, in any order (multiple orders measured), idempotently
   — duplicate `terminated` tolerated (delve sends two) — flushing
   pending callbacks with a synthetic failure exactly once. Shutdown is a
   policy *matrix*, not one verb: the session retains whether it was
   **launched or attached**, `dap-disconnect` means
   `disconnect {terminateDebuggee:false}` (detaching is its purpose),
   `dap-terminate` means `terminate` when capable else
   `disconnect {terminateDebuggee:true}`, and default cleanup terminates
   a launched debuggee but only detaches an attached one (subplan 01 has
   the full matrix). For lldb-dap the *normal* teardown is the disconnect
   form since it lacks `terminate`. A timeout is not an error: after a
   timed-out `terminate` do not retry forever — close the transport (its
   close kills only a child the transport owns, as backstop).
9. **Breakpoints**: `setBreakpoints` replaces the whole set per source;
   responses zip positionally with the request; lldb-dap hands out a
   **new id on every re-send** for a moved breakpoint (re-key
   `hitBreakpointIds` after every set); debugpy's first id is **0** (use
   `bool has_id`, not a 0 sentinel) and it silently relocates
   out-of-range lines while calling them `verified:true` — always render
   the *returned* line; `line` may be absent on unverified breakpoints.
   lldb-dap also emits `breakpoint(reason:"changed")` events right after
   each set response — updates must be idempotent, and an unknown id
   with reason ≠ "removed" creates a client-side breakpoint (dape 0.17).
10. **Stepping**: adapters send `continued` after step requests even
    though the spec says they needn't — synthesize it locally on every
    successful step/continue *and* make the handler idempotent. The two
    all-threads flags have **deliberately different defaults**: absent
    (or false) `allThreadsStopped` means only the *named* thread is
    known stopped — nbcode's minimal stopped body must not mark every
    thread stopped — while absent `allThreadsContinued` means *all*
    threads continued. `stopped.threadId` is optional: with none,
    request `threads` and pick a stopped/first thread rather than
    issuing `stackTrace` with a guess. Honor `preserveFocusHint`:
    update panes and decorations, don't move focus. A `stopped` event
    can arrive **before** the `configurationDone` response (lldb-dap
    with stopOnEntry) — the stop handler must be safe while nominally
    configuring. Never switch UI on `reason` alone (lldb-dap's
    stopOnEntry says `"exception"/"signal SIGSTOP"`; nbcode's step says
    `"pause"`). Protocol IDs (`seq`, thread/frame ids,
    `variablesReference`) are stored as range-checked int32: the spec
    pins `variablesReference` to (0, 2³¹), and every ID all four
    measured adapters emitted fits — including lldb-dap's OS-tid thread
    ids; out-of-range is a logged protocol error, not a wider type.
11. **Stacks and sources**: fetch **one** frame on stop (both adapters
    have `supportsDelayedStackTraceLoading`; dape's `nof=1` +
    20-on-render is the model), everything deeper on demand. The very
    first lldb-dap stack already contains all three source failure
    modes: a real path, a debug-info-relative path that does not exist
    (`csu/libc-start.c`), and a synthetic frame with a non-zero
    `sourceReference`. Navigation must check the file exists before
    visiting, prefer the topmost frame whose source *is* openable, and
    leave other frames listed-but-non-navigable in v1. Ignore DAP
    columns for navigation in v1 (they are character positions in the
    adapter's notion of the file, not `row->chars` byte offsets —
    doc/coordinates.md gains a fourth space entry). Paths are native
    absolute (`pathFormat:"path"`), **not** URIs — do not reuse
    `lsp_uri`; `realpath()` before use as a breakpoint-table key.
12. **Output**: debugpy splits one `print` across two `output` events
    mid-line — append bytes, never treat one event as one line; lldb-dap
    emits CRLF. Route `stdout`/`stderr` to `*dap-output*`, `console` to
    the REPL, and **drop `telemetry` silently**. All of it renders
    through `display_glyph_at()` — adapter output is untrusted bytes and
    must never become terminal syntax (CLAUDE.md rule); do not advertise
    `supportsANSIStyling`.
13. **Events before the initialize response** (debugpy telemetry) are a
    spec violation that happens — buffer and accept. Ignore unknown
    events (`debugpySockets`, `module`, `process`, `loadedSource`) and
    unknown fields everywhere.
14. **Evaluate context matters**: on lldb-dap, `context:"repl"` returns
    LLDB-formatted `"(int) $0 = 21551"` (with a `$0` side effect) while
    `"hover"` returns bare `"32767"`. Panes use `hover`/`watch`; only
    `*dap-repl*` uses `repl`. A failed evaluate renders in place — it is
    not a session error.
15. **Timing**: debugpy is ~160 ms to initialize and a flat ~41 ms per
    round trip; lldb-dap 8 ms / 0-7 ms. PTY settle budgets are sized for
    debugpy under a sanitizer lane, not for lldb-dap on a quiet box — and
    the fake adapter is faster than both, so the real-adapter smoke
    cases are the only honest timing test.

The honest v1 initialize payload, measured sufficient for both adapters:
`{"clientID":"kg","clientName":"kg","adapterID":<per-adapter>,
"locale":"en-US","linesStartAt1":true,"columnsStartAt1":true,
"pathFormat":"path","supportsVariableType":true}` — and nothing else.
Every omitted flag is a promise not made (no paging, no progress, no
ANSI, no reverse requests). dap-mode's habit of impersonating VS Code and
advertising capabilities it doesn't implement (dap-mode.el:1175-1189) is
the anti-pattern.

## Architecture

```
dap_commands.c     cmdtable handlers; the only file that prompts
    │
    ├── dap_ui.c          *dap-* special buffers, layout, decorations
    └── dap_session.c     state machine, stop model, stop_epoch,
        │                 thread/frame selection, teardown lattice
        ├── dap_breakpoint.c   per-source table, markers, re-send policy
        ├── dap_config.c       .kg-dap.json / adapter specs / substitutions
        └── dap_client.c       seq spaces, pending table + deadlines,
            │                  event queue, reverse-request replies,
            │                  mutable capabilities
            └── dap_transport.c    stdio child | TCP connect; half-close
                └── framed_io.c    Content-Length framing (extracted)
                    └── json.c     (lsp_json renamed)
src/dap.h          the one editor-facing facade (+ WITH_DAP=0 stubs),
                   modeled on src/lsp.h / lsp_core.c
```

Dependency direction is strictly downward. `dap_client` and below know
nothing about buffers, windows or commands; `dap_ui` writes special
buffers only through the edit gateway (keeps the mutation-gateway census
clean); no DAP field lands in `struct editor_buffer`, `editor_window` or
`editor_config`. One active session in v1, but `struct dap_session`
carries `parent`/`children` and every command asks one
"which-session/which-thread" oracle function (dape's
`dape--live-connection` four-mode idiom, dape.el:1416-1455) so
multi-session later is confined to that seam. Messages are parsed off the
transport borrow one at a time and dispatched outside the read loop under
a per-poll work budget — DAP handlers *write* (reverse replies), and
dispatch-inside-read is the jsonrpc.el reentrancy bug class (bug#60088);
an unbounded drain-then-dispatch queue is the opposite failure, a peer
monopolizing the poll.

**Bounds discipline**: every adapter-controlled collection carries an
explicit limit before its parser or pane lands — pending requests,
queued messages/bytes and work per poll, threads, frames, scopes,
variable nodes and depth, transcript bytes (with a visible truncation
marker), config file size and expansion length, and a deadline for every
lifecycle step except launch (which is cancellable instead). Suggested
starting values live in the subplans; a generous limit is fine, an
absent one is not — this is `lsp_transport.h`'s own philosophy applied
up the stack.

## Stages

Detail lives in the subplans; each stage is one reviewable slice ending
with `make check` green plus the ratchet actions named in place.

- `doc/plans/dap/00-infrastructure.md` — everything before any DAP code,
  each piece valuable on its own: json/framed_io extraction + the two
  new transport entry points; `editor_async_*` at both poll sites; the
  `parse_escape()` CSI rewrite + F1-F12/M-arrows + PTY F-key tokens;
  keymap capacity + the startup-created `dap` minor map; `winmgr.h`
  migration + window-configuration save/restore + grid arrangement;
  `MAX_BUFFERS`.
- `doc/plans/dap/01-protocol.md` — `WITH_DAP` axis and facade; transport;
  client (seq, pending, deadlines, capabilities, reverse-request
  refusals); session state machine and teardown; breakpoints; stepping
  and the stopped-state model with `stop_epoch`; `fake_dap_adapter.py`
  with a scripted mode per measured fact; fuzzers; real-adapter smoke
  cases.
- `doc/plans/dap/02-ui.md` — `*dap-*` buffers and the one shared info
  map (RET dispatches on what the line is); source-line decorations; the
  six-pane layout on window configurations; F12 toggle + restore;
  output routing; keybindings and their documentation path; the REPL.
- `doc/plans/dap/03-java.md` — the first post-v1 adapter: Java via
  nbcode, **measured end-to-end on this box** (2026-08-11), including
  the `lsp-sibling` transport kind, the announce-scanner
  parameterization, the LSP-session prerequisites, and nbcode's
  choreography deviations; the jdtls + java-debug road assessed and
  recorded there, deferred.

## Decisions (settled with the user, 2026-08-11)

1. **Default key layout: gud-style**, matching the user's Emacs config —
   F4=evaluate, F5=step-in (C-F5 instruction granularity), F6=next,
   F7=step-out, F8=continue, F9=breakpoint toggle (C-F9 temporary),
   F10=until, M-F10=goto (capability-gated), F11=restart (the adapter
   `restart` request when advertised, client-side relaunch otherwise),
   M-F11=terminate, F12=layout toggle, M-up/M-down (and
   PageUp/PageDown) = frame up/down. Two minor maps, not one — the
   review caught that a session-only map contradicts the milestone's
   own first step (F9 *before* `dap-debug`): `dap-breakpoint` (F9, C-F9,
   active in ordinary file-visiting buffers whenever DAP is built)
   and `dap` (everything else, active only during a session, so F4-F8
   and F10-F12 never shadow users outside one). Both fully rebindable
   from init.el once the F-key names exist; VS Code-convention users
   rebind, README shows how.
2. **Launch configuration: kg-owned `.kg-dap.json`** at the project
   root, with the closed substitution set (`${file}`, `${fileDir}`,
   `${workspaceRoot}`, `${env:NAME}`) and verbatim `arguments`
   passthrough. No VS Code `launch.json` compatibility claim — dap-mode's
   path costs ~700 lines of sanitizer/expander machinery and a promise
   kg could only partly keep; dape reached the same conclusion.
3. **v1 session scope: single session**, refusing `startDebugging` with
   `success:false` + message and defaulting debugpy to
   `"subProcess": false`. lldb-dap loses nothing; Python loses only
   subprocess/multiprocessing debugging, recorded as the first
   follow-on. `struct dap_session` carries `parent`/`children` from day
   one so the later change is confined to the session oracle.
4. **Java LSP default: nbcode** (settled with the user 2026-08-11,
   resolving the review's server-selection blocker the direct way).
   kg's Java `server_specs[]` row switches from jdtls to nbcode on the
   listen-hash wire, started with both server flags; jdtls remains
   reachable as an override (`KG_LSP_SERVER_JAVA` / config). The switch
   is an LSP-side stage of subplan 03 with its own regression tests —
   it changes existing Java LSP behavior and installation expectations
   (`utils/install-nbcode.sh` is the installer), and that is accepted.

## Follow-ons (recorded, deliberate)

- **runInTerminal**: spawn the requested argv as an ordinary child with
  stdout/stderr piped into `*dap-output*` and reply `{processId}` — no
  pty needed for either target adapter (dape does exactly this); a real
  debuggee pty only matters for `isatty()`-checking programs.
- **startDebugging / child sessions**: debugpy subprocess debugging.
  Requires accepting the child config's `connect:{host,port}` promise
  (TCP transport already exists by then) and scoping breakpoint
  verification per session.
- **Java**: no longer speculative — planned in
  `doc/plans/dap/03-java.md` on the nbcode road, measured end-to-end on
  this box. (The jdtls + `com.microsoft.java.debug` road is assessed
  and recorded there, deferred: the plugin jar builds in 45 s but no
  jdtls exists here, and it needs a per-session
  mainClass/classpath resolver protocol nbcode doesn't.) One measured
  correction to the tree while there: the sibling announce is
  `Java Debug Server Adapter listening at port ...` — the comment at
  src/lsp_transport.h:100-104 omits the leading `Java `.
- **Breakpoint persistence** across kg restarts (dape/dap-mode both ship
  it; it is the "breakpoints are editor property, not session property"
  workflow completed).
- Watch pane and `setVariable`/`setExpression` editing; conditional /
  hit-count / log breakpoints UI (the wire fields ship in v1's structs);
  variable paging (only when kg actually sends `start`/`count` —
  advertising it unused is dap-mode's dishonesty); memory and
  disassembly panes (lldb-dap supports both); weighted window
  columns in `win_reflow()`; `cancel`/progress; a `POLLOUT`-carrying
  generalization of the editor wait seam (v1 accepts idle-tick latency
  for connect-in-progress and outbox flush, with the latency tested).

## Out of scope

launch.json task/variable machinery beyond the closed substitution set;
adapter acquisition/download (PATH + explicit path only, like LSP
servers); reverse debugging; multiple concurrent *root* sessions;
remote/cross-machine debugging (TCP connect ships loopback-first);
sandboxing debug configs (they run arbitrary commands by design — same
trust story as Lisp init files, and documented as such).
